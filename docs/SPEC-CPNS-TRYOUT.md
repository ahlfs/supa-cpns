# CPNS tryout module — design spec

Status: approved in conversation, awaiting written review
Date: 2026-11-15
Scope: one module added to the existing `supa-cpns` application
Supersedes: nothing

## 1. Purpose

`supa-cpns` today is a marketing site: one route, one controller, one database
table that is not used. This spec adds the thing the site is selling — an online
CPNS SKD tryout: account registration, a question bank, a timed exam engine that
scores itself, a score-analysis page, and an admin panel to write and assemble
the questions.

The exam is free. Every registered account can sit every package and read its
full analysis. There is no payment, no access lock, no ranking.

## 2. Decisions locked in conversation

| # | Question | Decision |
|---|----------|----------|
| 1 | Where it lives | One repo, one database, one deployment — a module of `supa-cpns`, not a second app |
| 2 | Commercial model | Free. Packages exist as entities, nothing is locked |
| 3 | Who writes questions | Admin panel in the browser, with an `admin` role |
| 4 | Accounts | Email + password, no email verification, no password-reset email |
| 5 | Answer saving | Auto-save on option click. No "Save and Next" button (differs from real CAT) |
| 6 | Screen support | Both taken seriously: real sidebar ≥992px, real bottom sheet below that |
| 7 | Depth of analysis | Medium: per-subtest, per-subtopic, timing, attempt history, explanations. No percentile |
| 8 | Architecture | Server-authoritative exam (approach 1 of 3) |
| 9 | Question edits after use | Allowed, always |
| 10 | Finish button | Enabled only when all 110 questions are answered |
| 11 | Leaving the exam | Allowed freely. `beforeunload` warns on accidental close only; no tab-switch tracking |
| 12 | Explanations | Shown immediately after submit |
| 13 | Package composition | Frozen once the package has its first attempt. Question text stays editable |
| 14 | Registration fields | Name, email, password. Participant number generated by the system |

## 3. Legal position on question content

Real CPNS question papers are not published by the state. Question banks sold or
published by third-party tryout platforms are copyrighted works; copying one and
rewording it produces a derivative work, not a new one, and putting it behind a
competing tryout product defeats the fair-use carve-out for education
(UU 28/2014 art. 44(1)(a), which requires that the source be credited and that
the author's legitimate interests not be harmed). Scraped-and-reworded items are
also trivially detectable: same options, same keys, same order.

Therefore: **all items are authored in-house against the official blueprint.**
The blueprint itself is public (KepmenPANRB 321/2024), and what copyright
protects is the expression of an item, not the fact that "pilar negara" is
tested. Published media example pages are used only to map which topics recur,
with attribution, never for item text. Two public repositories
(`henkiws/Simulasi-CAT-…`, MIT; `ainunnajib/lolos-cpns`, licence unverified) are
treated as structural reference only; a repository licence does not necessarily
cover a question file inside it.

Practical upside: every package can be guaranteed to hold exactly 110 items, TKP
items can be guaranteed to carry a full 1–5 weight ladder on their options, and
every item can have an explanation. Scraped banks routinely fail all three.

## 4. Scoring rules (authoritative)

Source: KepmenPANRB 321/2024 as published, cross-checked against the BKN
selection handbook and the `cat.bkn.go.id` simulation.

| Subtest | Items | Per item | Max | Passing threshold |
|---------|------:|---------:|----:|------------------:|
| TWK | 30 | 5 correct / 0 otherwise | 150 | 65 |
| TIU | 35 | 5 correct / 0 otherwise | 175 | 80 |
| TKP | 45 | option weight 1–5, unanswered 0 | 225 | 166 |
| **Total** | **110** | | **550** | all three, independently |

- Duration: 100 minutes. 130 for the `disabilitas sensorik netra` arrangement.
- There is no negative marking anywhere, and the worst TKP option still scores
  1 while an unanswered item scores 0. Leaving anything blank is therefore never
  optimal — this is a legitimate teaching point, not marketing.
- Thresholds are **independent**, not summed. A candidate can score 400 total
  and fail on TIU 70/80. The results page must make this unmistakable.
- Special-formation cumulative thresholds (311 with TIU 85 for cumlaude and
  diaspora; 286 with TIU 60 for disability and Papua) are stored in config but
  **not enforced**, because participants do not pick a formation. Wiring them up
  later is one dropdown.

## 5. Data model

Seven new tables plus three columns on `users`. `sessions`, `cache`, `jobs`
already exist and are kept as they are.

### 5.1 `users` (modified)

Add `role` (string, default `peserta`, cast to `App\Enums\UserRole`),
`participant_number` (string, unique, nullable, generated at registration), and
`must_change_password` (boolean, default false). Existing `#[Fillable]` /
`#[Hidden]` attribute style is kept; no array-style property is introduced.
`isAdmin()` becomes one line, and `Gate::before` in `AppServiceProvider` resolves
true for admins so future policies need no repetition.

### 5.2 `questions`

The bank, independent of any package.

| Column | Notes |
|--------|-------|
| `id` | |
| `category` | `twk` / `tiu` / `tkp`, cast to `QuestionCategory` |
| `subcategory` | kisi-kisi subtopic, e.g. `pilar_negara`, `deret_angka`, `pelayanan_publik` |
| `stem` | question text |
| `explanation` | why the key is the key |
| `is_active` | soft retirement without deleting history |
| timestamps | |

A question belongs to the bank, not to a package, so one item serves several
tryouts and admin never retypes it. This is what makes the bank compound instead
of becoming a stack of near-duplicate packages — and it is why freeing package
composition (decision 13) costs almost nothing.

### 5.3 `question_options`

Five rows per question, `label` A–E, `body`. Two mutually exclusive columns:

- `is_correct` — TWK and TIU only.
- `score` — TKP only, 1–5.

Which one applies is enforced in the admin `FormRequest`, not in the database,
because the rule differs per category and reads better in code. For a TKP item
the request additionally demands that the five scores are exactly 1, 2, 3, 4, 5
— two options sharing a weight makes the item worthless and must never save.
TWK/TIU items are rejected if any option carries a score.

### 5.4 `exam_packages`

`title`, `slug`, `description`, `duration_minutes` (default 100), `status`
(`draft` / `published`), optional `opens_at` / `closes_at`.

Publishing is refused server-side unless the package holds exactly 30 TWK, 35
TIU and 45 TKP items. A half-built package can never reach a participant, and the
refusal is in the controller, not only in a disabled button.

### 5.5 `exam_package_question`

Pivot: `exam_package_id`, `question_id`, `position`. Unique on
(package, question) and on (package, position), so no duplicate item and no gap
in numbering is possible.

### 5.6 `exam_attempts`

One row per sitting. `status` (`in_progress` / `submitted` / `expired`),
`started_at`, `expires_at` (= started + duration, computed server-side),
`submitted_at`, `current_question_id`, `last_activity_at`, and the frozen result:
`twk_score`, `tiu_score`, `tkp_score`, `total_score`.

### 5.7 `exam_attempt_answers`

One row per question per attempt. `selected_option_id` (nullable = skipped),
`is_correct`, `score_awarded`, `seconds_spent`, `is_flagged`, `answered_at`.
Unique on (attempt, question).

That unique key is what makes auto-save safe to fire repeatedly: clicking the
same option twice, tapping fast on a slow connection, or retrying after a failure
all collapse onto one row instead of stacking duplicates.

### 5.8 `exam_attempt_subtopics`

Per-subtopic rollup: `correct`, `wrong`, `blank`, `score`. This table is the
reason the analysis page stays fast; the alternative is recomputing 110 items on
every page view, which works until participant 500.

### 5.9 Two deliberate consequences

**Scores are frozen at submit, not recomputed on read.** `is_correct` and
`score_awarded` are stored per answer, and the subtopic rollup is stored. Editing
a question in the admin panel therefore does not move a finished participant's
score — which is correct: a grade must not change after the exam. Item text and
explanation are read live from the bank, so a typo fix reaches past participants
immediately. The rejected alternative (snapshotting item text into every attempt)
bloats the database and freezes the bank against correction.

**The analysis page only reads stored numbers.** An unsubmitted attempt has no
score, and no route may reveal one before submission.

## 6. Exam engine

### 6.1 Starting and resuming

`POST /tryout/{package}/mulai` creates an attempt with `started_at = now()` and
`expires_at = now() + 100 minutes`. If the user already has an `in_progress`
attempt on that package, the endpoint **resumes** it instead of creating a second
one: someone who closed the browser on question 40 returns to question 40 with
the clock still running. Starting fresh is a separate, explicit action that
abandons the old attempt.

### 6.2 The clock is the server's

The page renders a countdown from a server-supplied number, and every answer
response carries the refreshed remaining seconds. A paused tab or a changed
system clock is pulled back into line within one click. If the browser is closed
past expiry, a submit that arrives late is still graded as `expired`, because the
grading service — not the browser — checks `expires_at`.

Expiry is therefore evaluated **on the read path**: opening the package list,
the exam room, or the dashboard closes and grades any attempt whose time is up.
The application is correct with no cron at all. A scheduled sweep
(`cpns:expire-attempts`) ships as an optional complement, and
`schedule:run` in `deploy/host-cpns.sh` stays commented out until asked for.

### 6.3 Saving an answer

`PUT /tryout/attempt/{attempt}/jawaban` takes `question_id`,
`selected_option_id` (nullable for "skip") and `is_flagged`, and upserts the
single row for that (attempt, question).

- The option recolours locally on click; the request goes out behind it. Auto-save
  must feel instant, but the server stays the source of truth.
- On failure the option reverts and a small marker appears — a participant on a
  weak connection must never be told "saved" when it was not.
- No Save button, per decision 5. A transient "tersimpan" indicator fades after
  each successful write.
- Only the answer is sent. The browser never uploads a whole exam state blob and
  the server never accepts one: each write names exactly the question it is about,
  so a lost or duplicated request can only affect that one item.
- A write is rejected if the attempt is not `in_progress`, if the attempt has
  expired, or if the question is not in this package.

### 6.4 Time per question

`current_question_id` plus `last_activity_at` close an interval whenever the
participant moves on, and the seconds go to that question's answer row, capped at
five minutes per question so an abandoned tab cannot absorb half an hour. This is
an estimate, labelled as one in the UI: it answers "which item ate your time", it
is not forensic evidence.

### 6.5 Grading

One service, invoked once, at submit. TWK and TIU: correct 5, otherwise 0. TKP:
`option.score`, blank 0. Results are frozen onto the answer rows and rolled up
per subtest and per subtopic. Thresholds live in `config/cpns.php` (65/80/166,
150/175/225, 550) so no number is hard-coded in a view.

### 6.6 Finishing

`POST /tryout/attempt/{attempt}/selesai` refuses unless all 110 questions have an
answer row with a selection — enforced in the controller, not only by disabling a
button. The UI shows one confirmation naming how many items are still blank.
Expired attempts are graded without that check.

### 6.7 Composition lock

Once a package has any attempt, the pivot rows are immutable. Every mutating
admin endpoint on the pivot is refused with a clear message pointing at "create a
new package". Editing the items themselves stays open everywhere.

## 7. Exam room UI

### 7.1 Its own layout, on purpose

The exam room does **not** reuse the marketing header and footer. The marketing
header carries a mega menu and site-wide links, and one stray click during a
100-minute timed exam costs the participant something that cannot be bought back.
`resources/views/components/layouts/exam.blade.php` is a thin bar plus a content
slot. Same tokens, so it still looks like the same product.

`beforeunload` is registered while an attempt is open — protection against a
mistaken close, not surveillance (decision 11).

### 7.2 ≥992px (desktop)

Three columns, CAT-shaped:

- Left: a sticky 110-cell navigator with its own scroll. Cells use the existing
  `success` and `danger` tokens — answered green, unanswered red — and with
  auto-save the cell flips green the moment the option is clicked. Clicking a cell
  jumps to that item. A small dot marks a flagged item.
- Top strip: name, participant number, end time, item count, answered, not
  answered, countdown, and Finish — disabled until 110/110.
- Centre: subtest label, stem, five options, then Previous / Skip this item /
  Next. No Save button.
- The countdown turns `warning` inside 10 minutes and `danger` inside 5.
- Keyboard: `A`–`E` select, left/right arrows move between items.

The flag ("ragu-ragu") and the countdown colour changes are **our additions**,
not features of the BKN CAT we verified. They are called out as such so nobody
later mistakes them for a faithful copy.

### 7.3 <992px (phone)

A genuinely different shape, not a shrunken one:

- Sticky top bar: large countdown, current item number, and a button that opens
  the navigator.
- Single full-width column, stem at 16px, options as cards with ≥44px touch
  targets — a mis-tap here changes an answer.
- Sticky bottom bar: Previous, "item n of 110", Next.
- The navigator is a bottom sheet, 5 columns. **Finish lives inside the sheet**,
  deliberately not in the main screen, so nobody ends the exam at item 60 by
  reaching for Next.
- Wake lock is requested while the exam is open, so the screen does not sleep
  mid-item. It needs nothing from the server.

### 7.4 One engine, two faces

`resources/js/modules/exam.js` follows the existing data-attribute module pattern
(`carousel.js`, `header.js`). State is read from `data-*` attributes; the desktop
and phone layouts differ only in CSS at the 992px breakpoint. There is no second
code path to keep in sync. No new npm dependency is added.

## 8. Score analysis

One page per attempt, readable only by its owner. An unsubmitted attempt shows no
numbers and redirects to the room or to the attempt list.

Top to bottom:

1. **Total card** — score, of 550, pass/fail.
2. **Three subtest cards** — score, max, correct/wrong/blank, and a bar with a
   tick exactly at the threshold, so "10 short of the line" is visible without
   arithmetic. The card states that thresholds are independent. TKP additionally
   shows average option weight, which reveals a participant who consistently
   picks low-value options.
3. **Per-subtopic breakdown**, weakest first — reads the rollup table. This is the
   part that answers "what do I study", and it is the most-visited part in
   practice, not the total.
4. **Timing** — total used of 100 minutes, average seconds per item, and the five
   slowest items. Plus one small panel derived from stored data with no extra
   table: items answered in under 10 seconds *and* wrong, which are near-certainly
   guesses. Labelled as an estimate.
5. **Attempt history** — a server-rendered SVG line chart: total plus three
   subtest lines across attempts in the same package, with dashed threshold
   markers, and a table of date, score, duration, and delta from the previous
   attempt. Self-comparison only; no percentile, because a percentile computed
   from five participants makes the product look empty. No chart library: the
   project has none, the shape is a handful of points and lines, and a 200KB
   dependency is not proportionate.
6. **Explanations** — all 110 items with the participant's answer, the key, and
   the explanation, filterable to all / wrong / blank / correct.

"Repeat the items you got wrong" is deliberately **not** a button yet. The bank
already splits items from packages, so a practice session can be built on top of
this later without new tables — but practice mode is a later phase, and a button
that half-works is worse than an accurate list.

## 9. Admin panel

New `admin` layout: left sidebar, right content, no marketing footer. Third
layout in the app (marketing, exam, admin), all sharing the same tokens. Icons
come from the existing `<x-icon>` component, which reads real SVG files from
`resources/icons/` via `App\Support\Icon` — never an emoji, per house rule.

Routes live in `routes/admin.php`, not `routes/web.php`, behind the `admin`
middleware alias registered in `bootstrap/app.php`.

Five screens:

1. **Dashboard** — items per category, draft vs published packages, participant
   count, and the list that actually gets used: packages that are not yet 110,
   with the shortfall per subtest.
2. **Question list** — filter by category and subcategory, text search, and a
   mandatory column showing which packages use the item and how many. Since
   question edits are always allowed (decision 9), this column is what makes that
   safe: the admin sees the blast radius before saving.
3. **Question form** — one form, two faces. TWK/TIU: five options with one key
   radio. TKP: five options, each with a 1–5 weight dropdown, and no key radio at
   all, because in TKP every option is correct and only the weight separates
   them. Validation per §5.3. Subcategory is chosen from the kisi-kisi list
   defined in `config/cpns.php`.
4. **Bulk import** — paste a fixed-column text block or upload CSV. Always
   through a dry-run preview: rows read, rows valid, rows failed with line numbers
   and reasons, and Save enabled only after the preview. **All-or-nothing:** one
   bad row means nothing is written. A half-finished import into a live bank is
   far worse than a refused one, because a broken item is only discovered when a
   participant meets it. The accepted columns are
   `category, subcategory, stem, option_a…option_e, key, explanation` for TWK/TIU
   (where `key` is a letter) and `category, subcategory, stem, option_a…option_e,
   score_a…score_e` for TKP (where the five scores must be 1–5), with a header row
   required. `docs/QUESTION-IMPORT-FORMAT.md` ships with a worked example per
   category.
5. **Package builder** — search and filter the bank, move items into a package,
   reorder them, with a TWK 30 / TIU 35 / TKP 45 shortfall bar on top. Publish is
   refused server-side until the composition is exact (§5.4). Title, slug,
   description and duration are edited here.

Two supporting pieces:

- **First admin account** via `php artisan cpns:admin` — not a seeder with a
  default password that survives on a server.
- **Password reset through the panel.** Because email is dead, an admin triggers
  a reset and the system generates a temporary password shown **once on screen**:
  not emailed, not logged. The account is flagged `must_change_password`, and
  middleware forces the change before anything else. Without that flag the
  temporary password becomes permanent, which is the classic hole in an app with
  no mailer. `password_reset_tokens` stays unused — stated plainly so nobody
  wonders what it is for.

Audit logging (who changed what) is **out of scope now**. The "used in which
packages" column covers the real risk; a full trail is its own project.

## 10. Accounts and roles

Session guard, written by hand — no Breeze. The requirement is four routes
(login, register, logout, change password), and pulling in a full scaffolding
package for that is not proportionate. No Livewire or Inertia either: the repo's
pattern is Blade plus data-attribute JS modules, and a second paradigm in one
application costs more than it saves.

- Routes: `GET|POST /masuk`, `GET|POST /daftar`, `POST /keluar`,
  `GET|POST /akun/password`. The login route is named `login` because Laravel's
  `auth` middleware already redirects guests to the route of that name.
- Controllers: `App\Http\Controllers\Auth\{LoginController, RegisterController,
  PasswordController}` — three small single-purpose files.
- Registration collects name, email, password. A unique `participant_number` is
  generated and shown in the exam bar. Email is **not** entered twice: the extra
  friction would only paper over a problem better solved in the panel, where an
  admin can fix a mistyped address.
- Middleware: `auth` for `/dashboard`, `/tryout`, `/hasil`; alias `admin` for
  `/admin`; and `password.changed` for the forced-change flow.
- Password rule: minimum 8 characters with letters and numbers. Session
  regenerated on login, invalidated on logout. Login throttled to 5 attempts per
  minute per email+IP.
- `SESSION_LIFETIME` rises from 120 to 1440 minutes: a two-hour session logs
  people out between practice sittings for no benefit. "Remember me" is enabled,
  since `remember_token` already exists.
- Honest limitation: with no mailer, an address cannot be proven to belong to the
  registrant, and `email_verified_at` stays unused. The single mitigation is the
  admin's ability to correct a participant's email, which is why registration
  does not demand it twice.

Modified: `routes/web.php`, `resources/js/app.js`, `app/Models/User.php`,
`app/Providers/AppServiceProvider.php`, `bootstrap/app.php`, `resources/css/app.css`

Constraints inherited from the existing build, to be respected in every new view:

- Every new Blade file lives under `resources/views`, because Tailwind runs with
  `source(none)` and only scans `views`, `js`, and `content`.
- Base value plus `lg:` only; never `md:` and `lg:` on one property (`lg` = 992px).
- Tailwind utilities only — no new CSS files, no BEM, no `<style>` blocks.
- Icons are real SVG files via `<x-icon>`. Images via `<x-ui.image>`. No emoji,
  no icon fonts, no remote URLs.

## 12. Verification

Automated, `php artisan test`:

- Scoring arithmetic: 30×5 = 150 and 35×5 = 175, TKP all-5s = 225, total 550,
  blank TKP = 0, TWK/TIU wrong = 0.
- Thresholds are independent: a 400-total attempt with TIU 70 is a fail.
- Expiry on the read path grades a timed-out attempt without any scheduler.
- Answer upsert is idempotent: the same option twice leaves one row; changing an
  option updates that row.
- Finish is refused with one blank item, accepted at 110/110.
- Publish is refused at 109 items and at a wrong category split (e.g. 31/34/45).
- Pivot is immutable once an attempt exists; editing an item still succeeds.
- Import is all-or-nothing: one malformed row writes nothing and reports its line.
- TKP form rejects two options sharing a weight and rejects a scored TWK item.
- Role gate: a `peserta` gets 403 on every `/admin` route.
- `must_change_password` blocks every route except the password form.
- A participant cannot open another participant's result page.

Browser, extending `tools/live-smoke.mjs` against the deployed site: start a
package, answer and skip items, jump via the navigator, flag an item, resume after
a reload with the clock advanced, finish, and load the results page with its
chart. Run at 1440 / 768 / 390 — the phone run is the one that matters for the
bottom sheet and touch targets.

Manual check before it is called done: sit one full 110-item attempt on a phone.

## 13. Out of scope

Named explicitly so they are not silently assumed: payment and package locking,
email verification and password-reset email, practice mode with per-item
explanations, a generated "repeat your wrong answers" session, percentile and
leaderboard, certificates, audit log, formation-specific thresholds in the UI,
the 130-minute netra arrangement as a selectable option, question versioning, and
CAT-faithful "Save and Next" mode.
